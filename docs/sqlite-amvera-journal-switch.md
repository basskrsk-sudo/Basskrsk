# ХвостМаркет — плановое переключение SQLite WAL/DELETE на Amvera

> **Режим приложения сейчас WAL (показан в админке 21.11.2026).**
> Эта инструкция — для оператора во время планового обслуживания. Само наличие
> этого документа и скрипта **не меняет базу**. Не выполнять в рабочее время.

## Подтверждённые факты

* На снимке от 21.11.2026: `PRAGMA integrity_check = ok`, нарушений FK = 0.
* Снимок из `VACUUM INTO` показывает DELETE независимо от исходного WAL:
  смотреть **только** «Система → Мониторинг → Режим SQLite на Amvera».
* Локальный тест 80 транзакций на копиях реальной базы показал преимущество
  WAL; Amvera отдельно предупреждала о высокой нагрузке WAL на `/data`.
  Без результатов именно на `/data` улучшение после перехода **не доказано**.
* Сайт работает с реальными заказами/ЮKassa. Старый бэкап нельзя просто
  восстанавливать поверх более новых заказов.

## Предварительные условия (все обязательны)

1. Убедиться, что в GitHub прошли CI, а Amvera развёрнута с этим изменением.
2. Выбрать окно с минимальным трафиком. Остановить приём новых покупок
   на время перезапуска; проверить отсутствие обрабатываемых платежей.
3. Скачать **новый** консистентный бэкап из «Управление системой →
   Резервные копии → Скачать бэкап сейчас» и сохранить **вне Amvera**.
   Старого снимка 07:59 UTC недостаточно как актуального отката.
4. Проверить файл локально:
   `node scripts/sqlite-offline-verify.js --source ПУТЬ_К_ФАЙЛУ.db`.
   Записать SHA-256; файл не отправлять в GitHub.
5. Настроить **одну** реплику Amvera. Не запускать одновременно несколько
   экземпляров с одним файлом `/data/taiga.db`. Для процедуры выключить
   приложение/приём запросов и перезапустить в одиночной реплике.
6. Согласовать способ проверки тестовой оплаты/отмены. Провайдер ЮKassa
   должен безопасно обработать повторные webhook после перезапуска.

## Однократный запуск процедуры (только в окне обслуживания)

В настройках Amvera временно задать:

```dotenv
HM_SQLITE_JOURNAL_TARGET=DELETE
HM_SQLITE_MAINTENANCE_CONFIRMED=OFFSITE_BACKUP_VERIFIED_SINGLE_REPLICA_MAINTENANCE
HM_SQLITE_OFFSITE_BACKUP_SHA256=<sha256 внешнего проверенного бэкапа>
```

При следующем запуске `server/server.js`, **до открытия основной базы и
запуска HTTP**, будет:

* проверен текущий режим;
* сделан свежий снимок в закрытом каталоге `/data/.sqlite-maintenance-backups`
  (это дополнительная копия, не замена внешнего бэкапа);
* проверены целостность, FK, схема и число ключевых записей;
* для WAL выполнен контрольный checkpoint;
* установлен режим DELETE и выполнена повторная проверка.

Если появляется SQLITE_BUSY, ошибка проверки или неверный режим — запуск
прервётся, автоматической подмены базы не будет. **Не удалять** `-wal/-shm`
вручную, не пытаться «исправить» старым бэкапом. Нужна проверка специалиста.

## Сразу после запуска

1. Проверить «Система → Мониторинг → Режим SQLite на Amvera»: должен быть DELETE.
2. Удалить **все три** временные переменные Amvera, чтобы не повторять
   процедуру при будущих деплоях. Перезапуск без них не меняет режим.
3. Проверить QR→карточка→ЮKassa sandbox→webhook→оплаченный заказ, а также
   отклонённый платёж и освобождение резерва без двойного списания.
4. Сравнить с периодом до переключения: p95/p99 Event Loop, задержки SQLite
   и `/data`, тайм-ауты внешнего GitHub uptime мониторинга, заказы и склад.
   Наблюдать не менее двух ночей. **DELETE может быть медленнее**, особенно
   когда работает несколько читающих потоков.

## Если DELETE существенно хуже

Не восстанавливать старый снимок поверх новых заказов. Снова сделать новый
внешний бэкап и подтвердить SHA-256. В отдельное окно обслуживания разрешён
симметричный переход:

```dotenv
HM_SQLITE_JOURNAL_TARGET=WAL
HM_SQLITE_MAINTENANCE_CONFIRMED=OFFSITE_BACKUP_VERIFIED_SINGLE_REPLICA_MAINTENANCE
HM_SQLITE_OFFSITE_BACKUP_SHA256=<sha256 нового внешнего бэкапа>
```

Затем проверить сайт и удалить переменные. Реверс WAL опасен на
сетевом хранилище, где Amvera рекомендует DELETE; использовать лишь
после анализа фактических ошибок и рисков.
