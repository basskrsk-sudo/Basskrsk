# Контроль доступности ХвостМаркет без отдельного сервиса

## 1. Что работает после обновления Amvera

- `GET /api/live`: отвечает `200 {"status":"ok"}`, когда HTTP-процесс Node.js жив.
- `GET /api/health`: отвечает `200` только при доступности SQLite и возможности записывать во временный файл постоянного хранилища `/data`. При проблеме — `503` без раскрытия путей, паролей и деталей базы.
- `GET /api/admin/system-health`: сведения о памяти, приблизительной CPU-нагрузке процесса на одно ядро, задержке Node.js, доступном диске и истории перезапусков. Доступно **только активным администраторам**.
- Админка сайта → **Система → Мониторинг**; Telegram Mini App → **Администратор → 💓 Состояние системы**.
- Node.js сохраняет время запуска и heartbeat в SQLite, фиксирует восстановление после заметного перерыва, предупреждает Telegram о высоком использовании ресурсов и отказах БД/диска (если Telegram настроен в Amvera). Срок хранения локальных событий — 90 дней.

> Встроенный мониторинг не может сообщить об аварии, когда Node.js полностью остановился или сеть Amvera недоступна. Независимую проверку выполняет GitHub.

## 2. Независимая проверка GitHub Actions

Файл `.github/workflows/site-uptime.yml` запускает `scripts/site-uptime-monitor.js` с периодом **каждые 5 минут** (фактический запуск может задерживаться по правилам GitHub Actions).

Проверяются:

1. `https://хвостмаркет.рф/` — HTML главной.
2. `https://хвостмаркет.рф/api/health` — SQLite и хранилище.
3. `https://хвостмаркет.рф/api/points` — работа публичного API.
4. `https://хвостмаркет.рф/miniapp.html` — HTML мини-приложения.

Каждая проверка ограничена 8 секундами. При ошибке выполняется **повторная проверка через 20 секунд**. Если один и тот же компонент не работает дважды, в репозитории автоматически открывается GitHub Issue `[Мониторинг] ХвостМаркет — сайт недоступен`. Пока инцидент открыт, новые Issues и повторные тревоги не создаются. После **двух полностью успешных** проверок инцидент закрывается и отправляется сообщение о восстановлении.

GitHub Issue — постоянный независимый журнал случаев недоступности. Если GitHub или Telegram временно недоступны, нужно смотреть журнал выполнения workflow.

## 3. Включить Telegram-уведомления (одноразовая настройка)

Монитор может отправлять сообщения **напрямую через Telegram API**, даже когда сервер Amvera полностью выключен.

Требуется вручную добавить в GitHub репозиторий
`basskrsk-sudo/Basskrsk` → **Settings → Secrets and variables → Actions → New repository secret**:

| Имя секрета | Что вводить |
|---|---|
| `HM_MONITOR_TELEGRAM_TOKEN` | Токен Telegram-бота для служебных уведомлений. Можно использовать существующий токен `@HvostMarketRusBot` из секретов Amvera или завести отдельного бота мониторинга |
| `HM_MONITOR_CHAT_ID` | Telegram `chat_id` личного служебного чата либо группы, куда бот имеет право писать |

Не отправляйте токен или chat_id в публичный код, Issues, чаты партнёров или скриншоты. Для личного чата сначала нажмите **Start** у бота; для групп добавьте бота с разрешением отправлять сообщения.

**Если секреты ещё не добавлены**, GitHub Issues уже регистрирует инциденты и автоматически закрывает их при восстановлении. Уведомления Telegram начнут работать после добавления обоих секретов. Если сайт уже находится в аварийном состоянии, монитор повторит отправку оповещения в следующем цикле.

Использование существующего бота для отправки **не требует останавливать его long polling**: отправка сообщений через Telegram Bot API независима от получения обновлений.

## 4. Первый запуск и проверка

1. Дождаться завершения развёртывания в Amvera. Проверить в Safari/Chrome, что `https://хвостмаркет.рф/api/health` возвращает `{"status":"ok"}` (а в JSON обе проверки `ok`).
2. Открыть GitHub → **Actions → HvostMarket site uptime → Run workflow**. Оставить **test_notification = false** и нажать **Run workflow**: это настоящая проверка главной страницы, SQLite, каталога и Mini App.
3. Посмотреть результат в Actions, затем открыть админку → **Система → Мониторинг**.
4. Для проверки доставки в Telegram повторить **Run workflow**, установив флажок **test_notification = true**. Этот режим **отправляет только одно тестовое сообщение** и не создаёт инцидент, не прерывает работу Amvera, не проверяет и не затрагивает платежи. Если задача завершилась ошибкой, проверить секреты `HM_MONITOR_TELEGRAM_TOKEN` и `HM_MONITOR_CHAT_ID`, доступ бота к чату и разрешение на отправку.
5. Убедиться, что в Telegram пришло сообщение **«🧪 ХвостМаркет: тест уведомлений мониторинга GitHub Actions»**. Снимать/поднимать настоящий сайт для тестирования запрещено.

Для корректной работы workflow в настройках GitHub Actions должны быть разрешены workflows; права `issues: write` уже указаны в YAML.

## 5. Встроенные оповещения Amvera

В панели Amvera отдельно включите email-уведомления о сбоях проекта. Если тариф/интерфейс поддерживает HTTP readiness/liveness-пробы, укажите:

- liveness: `/api/live`
- readiness: `/api/health`

Не считайте проверку снаружи доказательством причины. При инциденте сравнивайте время GitHub Issue с логами Amvera, перезапусками контейнера, нагрузкой на память и сообщениями `SQLITE_BUSY`, `SQLITE_FULL`, `out of memory`. Измерения CPU и памяти относятся к приложению, не к пользователям сайта.

## 6. Ограничения

- Внешний мониторинг зависит от GitHub Actions; это не SLA и не замена профессиональному геораспределённому мониторингу.
- Показатели внутреннего мониторинга доступны только пока сервер и авторизация работают.
- Heartbeat записывается раз в минуту. Перерыв между сердцебиениями после перезапуска — оценка, а не точная длительность простоя.
- Данные мониторинга не содержат телефонных номеров клиентов, токенов, содержимого заказов или приватных файлов.
- Мониторинг не должен автоматически перезапускать сервер, пересоздавать заказы, выполнять оплату или откатывать базу.
