# Снятие зависших резервов перед переходом на 1 минуту

**Важно:** речь только о *зарезервированных неоплаченных товарах*.
Не меняйте `stock.qty` вручную и не освобождайте оплаченные заказы:
это может привести к продаже одной упаковки двум покупателям.

## Запуск на действующей базе Amvera — до обновления main

1. Убедитесь, что доступен штатный **резервный снимок работающей SQLite базы**.
   Важно: использовать рабочую базу контейнера и текущие ключи ЮKassa.
   Локальный файл или старый скачанный бэкап не изменит остатки на сайте.
2. Скопируйте файл `server/reservation-predeploy-release.js` **из этого PR**
   в рабочую директорию Node.js приложения (рядом с `server/db.js`) через
   доступный вам механизм Amvera. Публиковать новую версию в `main` для
   исполнения этого файла **не требуется**.
3. Сначала проверьте количество кандидатов, не меняя базу:
   ```sh
   node server/reservation-predeploy-release.js --dry-run
   ```
4. Для безопасной сверки с ЮKassa и освобождения товаров из отменённых заказов:
   ```sh
   node server/reservation-predeploy-release.js --execute
   ```
5. Ознакомьтесь с итоговым JSON. `released` — реально возвращённые
   резервы. `paid_or_succeeded` — оплаченные, **их нельзя возвращать в
   продажу**; обработка подтверждения оплаты проводится штатным механизмом
   сайта. `unresolved`, `awaiting_payment_identifier`, `errors` требуют
   отдельной сверки — товар оставлен заблокированным сознательно.
6. Сверьте карточки проблемных точек, доступные остатки и журнал ЮKassa.
   **Только после проверки** сливайте PR с настройкой 60 секунд в main.

## Гарантии

- Рассматриваются только `pending`-заказы с `active` резервом старше 60 секунд.
- Для платежа с ID выполняется запрос статуса в ЮKassa. Для
  `pending`/`waiting_for_capture` запрашивается отмена.
  Возврат товара разрешается **только** при статусе `canceled`.
- Нет ID платежа или ЮKassa недоступна — остаток не меняется.
- Списание косточек и промо-блокировок возвращается вместе с товаром
  через транзакцию приложения, не прямым SQL.
- Операция идемпотентна: повторное исполнение не увеличит остатки дважды.
- Никакой массовой корректировки физического склада не происходит.

## После обновления

Новые неоплаченные заказы резервируют товар на **60 секунд** (старое значение
`RESERVATION_TTL_MINUTES=15` игнорируется). Проверка запускается примерно
у истечения самого раннего резерва; когда нет активных заказов,
лишние проверки не выполняются. При ошибках сети/API резервы сохраняются
до подтверждения безопасной отмены и проверяются повторно.
